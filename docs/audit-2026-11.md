# Code audit, November 2026

An audit of `ai-desktop` at commit 1d90d08 (version 0.4.0 plus the unreleased work that became 0.5.0).
It is kept here as the work list for the fixes planned for 0.5.0 and later.

## How this audit was done

Thirteen reviewers each read one area of the code; every finding was to be checked by an
independent reviewer. The run was cut short by a usage limit: nine areas were reviewed, four
(documentation, security and privacy, cross-platform, architecture) were not, and almost no
finding got its independent check. The most serious findings were then checked by hand against
the code, real `xrandr` output and the installed pyautogui and MCP SDK sources.

**Status** in the lists below:

- **verified**: reproduced or confirmed against the code by hand.
- **unverified**: reported by one reviewer, not yet checked. Each fix starts with a test that
  reproduces the problem; a finding whose test cannot be made to fail is dropped.

used; the edges, the safety net and the untested platforms are where it is weak.

## CLI plumbing, output contract, global state and the action log

Score 7: Well-structured plumbing: globals are saved and restored, global flags work on both sides of the subcommand, the log never breaks a command and redacts text, and tests cover most of it. Gaps are edge cases: dash-leading values, tool timeouts escaping as tracebacks, multi-line or unescaped text output, one redaction hole, and untested non-UTF-8 stdout.

### CLI rejects option values that begin with a dash (type --text -la, screenshot --zoom -1500,300)

`cli-core-1` · medium · bug · **verified** · `ai_desktop.py:3912`

argparse treats a value starting with '-' as an option, so `type --text "--force"`, `paste --text -x`, `focus --title -draft` and `screenshot --zoom -1500,300` (a monitor left of the primary) exit 2 with 'expected one argument'. Only the MCP wrappers work around it.

*When:* Agent runs `ai-desktop type --text "-la"` or `screenshot --zoom -1500,300`, or MCP run(steps=[["type","--text","--force"]]): nothing is typed and the error is a usage block.

*Fix:* Before parse_args (in execute and parse_quiet) join single-value options (--text, --title, --app, --zoom, --url, --key, --keys, --id) with their next token as --flag=value; add CLI tests; document it.

### Tool timeouts and other non-CliError exceptions escape as a traceback; --json prints nothing

`cli-core-2` · medium · robustness · **verified** · `ai_desktop.py:4099`

execute() re-raises everything except CliError, OSError and KeyboardInterrupt. subprocess.TimeoutExpired from the capture tool (30 s) and the clipboard tools (15 s) is never converted, so screenshot, --seen, wait, copy and paste end with a Python traceback: no ERROR line, no JSON object.

*When:* gnome-screenshot or wl-paste hangs (locked screen, permission prompt) during `--json screenshot`: after 30 s stdout is empty and stderr holds a traceback. Also `run --file` with non-UTF-8 bytes, or AI_DESKTOP_UINPUT_DELAY=abc.

*Fix:* Convert subprocess.TimeoutExpired/SubprocessError to CliError at the call sites; in main() catch the rest, emit fail('internal error: ...') and print the traceback only with AI_DESKTOP_DEBUG=1.

### Unbalanced-quote error of a run step copies the typed text into the action log

`cli-core-3` · medium · privacy · **verified** · `ai_desktop.py:3551`

split_step puts the whole step string in its error ({step!r}). That error is stored unredacted in the run entry of the action log, although the neighbouring code and test_run_keeps_unquoted_text_out_of_its_error deliberately keep unquoted --text out of errors and the log.

*When:* run --steps '["type --text my password is hunter2, don't share"]': the apostrophe raises 'No closing quotation', and stderr plus the log line contain the full text.

*Fix:* Report only the step number, the command name (first word) and the shlex reason; add a test asserting the text is absent from stderr and from the log file.

### Text-mode output crashes on a non-UTF-8 stdout (Windows pipes) when a title or path has other characters

`cli-core-4` · medium · portability · **unverified** · `ai_desktop.py:147`

status(), windows, log and run print through sys.stdout's locale encoding with strict errors. On Windows with piped stdout (cp1252 before Python 3.15) a window title with CJK, emoji or a bullet dot raises UnicodeEncodeError: a traceback after the action ran. print_text already avoids this for copied text.

*When:* A Windows agent captures stdout of `ai-desktop windows` or `focus --title Code` while VS Code shows its unsaved-file dot in the title or a browser tab has non-Latin text.

*Fix:* At the start of main(): sys.stdout.reconfigure(encoding='utf-8', errors='backslashreplace') (stderr too), matching print_text; add a test using a cp1252 TextIOWrapper as stdout.

### Bad run steps and bad MCP arguments return the whole multi-line argparse usage as the error

`cli-core-5` · medium · bug · **verified** · `ai_desktop.py:4044`

parse_quiet captures argparse's usage block together with its error line, so run-step errors and MCP bad-argument errors are six or seven lines with the real reason last. In text mode ERROR is no longer one line, and `log` prints the same block.

*When:* run --steps '[["click","--x","abc","--y","1"]]' or MCP click(button="foo"): stderr starts 'ERROR step 1 (click): bad arguments: usage: ...' followed by five more lines.

*Fix:* Parse quietly with an ArgumentParser subclass whose error() raises with only the message (no usage); collapse newlines in the text form of fail().

### format_fields does not escape quotes or newlines in key=value output

`cli-core-6` · low · bug · **unverified** · `ai_desktop.py:121`

format_fields quotes values containing whitespace but never escapes embedded quotes or newlines, and leaves values with quotes or '=' but no spaces unquoted. Window titles in the focus OK line and in log listings can be ambiguous or split the line in two.

*When:* `focus --title search` when the browser title is '"foo" - Search', or a screenshot path= value containing a quote or newline.

*Fix:* Use json.dumps(text) whenever the value has whitespace, a quote, '=' or a control character (cmd_windows already does this for titles); add tests.

### Environment flags are parsed inconsistently and bad values are ignored silently

`cli-core-7` · low · robustness · **unverified** · `ai_desktop.py:4070`

Boolean environment variables are parsed three different ways and unknown values are silently ignored: AI_DESKTOP_JSON rejects 'on' (LOG_TEXT accepts it), AI_DESKTOP_LOG=disabled keeps logging, and a set-but-empty or capitalised AI_DESKTOP_BACKEND fails every action with "unknown backend ''".

*When:* An MCP client env block with AI_DESKTOP_BACKEND="" or AI_DESKTOP_JSON=on, or a user exporting AI_DESKTOP_LOG=none expecting the log to stop.

*Fix:* One env_bool() helper (1/true/yes/on, 0/false/no/off, CliError otherwise) for all flags; strip and lowercase AI_DESKTOP_BACKEND, treat empty as auto, validate it in execute().

### Action log is created with default permissions and keeps window titles and URLs in full

`cli-core-8` · low · privacy · **verified** · `ai_desktop.py:1056`

The log folder and files are created with the process umask (typically 0755/0644), and entries keep every window title returned by `windows`, `focus --title` values and `launch-chrome --url` in full. Where the home directory is traversable, other local users can read them.

*When:* A multi-user machine with a 0755 home (older Debian/Ubuntu installs) or AI_DESKTOP_HOME in a shared folder; the agent calls `windows` while a private document or mail is open.

*Fix:* Create ~/.ai-desktop, logs and screenshots with mode 0o700 and files with 0o600 (os.open); document the stored titles/URLs or add a switch that reduces them to counts.

### log reads whole daily files for a few entries; log size is unbounded

`cli-core-9` · low · performance · **unverified** · `ai_desktop.py:1102`

read_log_entries loads each daily file completely to return 20 entries, and entries carry bulky results (full window lists, doctor rows, nested run results, screenshot metadata). Logs are pruned by age only, so a busy MCP session makes `log` slower and the folder unbounded.

*When:* A day of agent work with frequent `windows` and `run` calls (tens of MB of JSONL); every `log` tool call reads and splits the whole file.

*Fix:* Read backwards in blocks from the end of the file until `limit` lines are found; store list-valued results as counts; include logs in a size rule.

### Invocations with bad arguments never reach the action log, contrary to the README

`cli-core-10` · low · docs · **unverified** · `ai_desktop.py:4102`

Invocations rejected by argparse are never written to the action log (args is None), for the CLI and for MCP tool calls alike, although README says every command appends a line and every MCP call lands in the log. Malformed attempts leave no trace.

*When:* MCP click(button="foo") or CLI `click --x abc`: exit 2 or a tool error, and `ai-desktop log` shows nothing for it.

*Fix:* Log a minimal entry (command = first argv token, code 2, error without argument values), or state the exception in README's Action log section.

**Smaller notes (unverified):**

- ai_desktop.py:3656 doctor prints its rows before the OK line (intended per test_doctor_text_rows_then_status_line), unlike windows/monitors/log where the status line comes first; 'first stdout line is the status' does not hold for doctor.

- ai_desktop.py:3698 argparse shows internal function names: `--radius abc` gives "invalid parse value", `--spacing abc` gives "invalid _spacing value", `--max-width abc` gives "invalid _max_width value".

- ai_desktop.py:1166 RNG.seed() from a `--seed` inside a run step persists for later commands in the same process (MCP server); with `python ai_desktop.py mcp --seed N` the seed goes to the __main__ copy of the module, not the imported ai_desktop the server uses.
- ai_desktop.py:1044 log `ts` is naive local time without a UTC offset and is the finish time; format_log_entry (line 1118) shows only HH:MM:SS, so `log --limit 200` across days has no dates.
- ai_desktop.py:1057 concurrent appends from several processes are atomic on POSIX but not on Windows (O_APPEND is emulated by seek+write); a torn line is silently skipped by read_log_entries. Speculative, untested.
- ai_desktop.py:3650 cmd_run prints copied text with print() (locale encoding) while print_text (line 2380) writes UTF-8 bytes; same text, two encodings on Windows.
- ai_desktop.py:4081 an OSError raised while printing the OK line (BrokenPipeError when stdout is closed early) is reported and logged as a failed command although the action already ran.

- ai_desktop.py:120 text mode renders None/True as Python reprs (monitor=None, partial=True) while JSON gives null/true; two spellings for parsers to handle.
- ai_desktop.py:3642 in text mode a failed `run` drops the results of the steps that succeeded (e.g. text copied by step 1) because list fields never reach the ERROR line.
- ai_desktop.py:41 PIL (Image, ImageGrab, ImageFont, ...) is imported at module load for every command, including key, log and --version; lazy imports would cut per-call start-up time.
- ai_desktop.py:4017 `log --limit` and MCP log(limit=...) have no upper bound; a large value returns the whole history in one tool result.

**Improvement ideas:**

- A local session daemon (Unix socket or named pipe) that keeps the parser, input devices and last capture in memory, so CLI calls skip Python/PIL start-up; it is the natural base for caching and live streaming.
- Add a stable machine-readable `error_code` field (screen_changed, off_monitor, bad_arguments, timeout, failsafe) so agents can branch without parsing English messages.
- Make bad arguments honour --json/AI_DESKTOP_JSON: pre-scan argv for the flag and use a parser subclass whose error() raises CliError, giving one contract for every failure.
- A `watch --jsonl` mode that emits change events (diff regions, new frame paths) on stdout using the action-log schema, so a local agent can follow the screen live instead of polling.
- Version the log schema and add a session id per agent run, UTC timestamps with offset, size-based rotation, and `log --since/--command/--failed` filters.
- Parse and validate every AI_DESKTOP_* variable once into a settings object (reported by doctor) instead of scattered os.environ reads with differing rules.

## Grid overlay and the screenshot pipeline (zoom, shrink, pointer marker, metadata)

Score 7.5: Coordinate math, label placement and zoom held up in numeric checks (within 0.5 screen px, no label collisions) and are well tested. The gaps are at the edges: negative --zoom parsing on the CLI, `grid` output without metadata or retention, avoidable full-frame work per screenshot, default file permissions, and labels that hide screen-edge UI.

### --zoom with a negative X is rejected by the CLI in its documented form

`grid-shot-1` · medium · bug · **verified** · `ai_desktop.py:3808`

`screenshot --zoom -1420,400` exits 2 with "argument --zoom: expected one argument": argparse takes `-1420,400` for an option. README and AGENTS.md document `--zoom X,Y`; only the MCP wrapper avoids it by sending `--zoom=...`.

*When:* A monitor left of the primary on Windows or macOS (negative x): the agent reads label -1420 off the grid and runs `ai-desktop screenshot --zoom -1420,400`.

*Fix:* Before parsing, join `--zoom` and a following token matching ^-?\d+,-?\d+$ into one `--zoom=...` token; add a CLI test next to the MCP one and document the form.

### `grid` output has no metadata, so re-gridding it silently resets origin and scale

`grid-shot-2` · medium · bug · **unverified** · `ai_desktop.py:3262`

cmd_grid saves without the ai-desktop chunk. Feeding its output back to `grid` falls through to origin (0,0) and scale 1, so labels become image pixels, not screen coordinates. `--seen` on that file is refused for lacking a .raw.png.

*When:* `screenshot --monitor 1 --grid` (origin 1920,0) or any shrunk capture; `grid --input shot.png`; then `grid --input shot_grid.png --spacing 25`: labels are off by 1920 px or by the shrink factor.

*Fix:* Pass meta to save_image in cmd_grid (x, y, width, height, image_scale, spacing, zoom, raw = the source's sidecar name) and let regrid_source and load_reference follow that `raw` link.

### Re-gridded store screenshots are never pruned or listed

`grid-shot-3` · low · privacy · **unverified** · `ai_desktop.py:855`

cmd_grid (line 3262) writes `<stem>_grid.png` next to its input. For a store screenshot that name does not match STORE_NAME_RE, so the file is hidden from `screenshots list` and exempt from the 30-day and 2 GB retention rules.

*When:* `ai-desktop grid --input ~/.ai-desktop/screenshots/<shot>.png --spacing 50`, a use the README describes; each run leaves a full desktop image in the store for good.

*Fix:* For inputs inside the store, name the output through new_screenshot_path (or allow an optional `_grid` suffix in STORE_NAME_RE) and add a prune test for it.

### read_image_meta decodes the whole PNG to read one text chunk

`grid-shot-4` · low · performance · **unverified** · `ai_desktop.py:473`

`img.text` makes Pillow load the full image. Every `--seen` and `wait --changed` therefore decodes the raw copy twice (metadata, then pixels), and `grid --input` decodes three images.

*When:* Any guarded action (`--seen latest`), `wait --changed`, `grid --input`, or `screenshot -o` over an existing sidecar; the cost grows with capture size.

*Fix:* Read `img.info.get(META_KEY)` (Pillow writes pnginfo chunks before IDAT) and fall back to `img.text` only when absent; in load_reference take metadata and pixels from one open.

### The screenshot pipeline makes several avoidable full-frame passes

`grid-shot-5` · low · performance · **unverified** · `ai_desktop.py:2790`

Non-zoom captures are gridded at full resolution with three RGBA buffers, the pointer marker (line 2713) composites the whole frame again, LANCZOS then shrinks it, and the model-facing PNG (line 2820) uses the default compress level 6.

*When:* Every screenshot and every `--shot`; worst on multi-monitor or 4K-at-100% desktops, where roughly 250 MB of transient buffers are allocated.

*Fix:* Shrink first and draw with pixel_scale=shrink and k=1, as the zoom path already does; composite the marker on a cropped region; save the main PNG with compress_level 1 to 3.

### Screenshots are written with default permissions, and AGENTS.md recommends /tmp

`grid-shot-6` · low · privacy · **verified** · `ai_desktop.py:457`

save_image creates folders and files with the process umask (usually 0755 and 0644). AGENTS.md line 29 suggests `-o /tmp/screen.png`, which also writes `/tmp/screen.raw.png`: full desktop images at a predictable path any local user can read.

*When:* A shared or multi-user machine: another account reads /tmp/screen.png, or the store when the home folder is traversable, and sees mail, chats or passwords on screen.

*Fix:* On POSIX create the store with mode 0o700 and files with 0o600; change the AGENTS.md example to a path under the store or $XDG_RUNTIME_DIR.

### Edge labels hide much of the top and bottom strips of the screen

`grid-shot-7` · low · design · **unverified** · `ai_desktop.py:419`

X labels are 75%-opaque boxes on the first and last rows, enlarged by k before shrinking. They cover 46% of the top and bottom 20 screen px at 1920x1080, and 61% of the top and bottom 59 px on a 5760-wide desktop.

*When:* Targets in panels, tab strips, title bars, taskbars or docks at a screen edge: their text lies under the label boxes in every gridded screenshot, most of all on multi-monitor captures.

*Fix:* Draw edge labels in a margin added around the capture (record the padding in metadata and the OK line), or label one edge per axis and lower the box opacity.

### `grid` picks zoom spacings for a shrunk screenshot and draws a second grid over the first

`grid-shot-8` · low · bug · **unverified** · `ai_desktop.py:3256`

`candidates = AUTO_SPACINGS if scale == 1 else ZOOM_SPACINGS` treats an image_scale below 1 as a zoom. A shrunk screenshot re-gridded from its own metadata gets spacing 100 (32 lines, 58 px apart) on top of its existing grid.

*When:* A multi-monitor screenshot (image_scale 0.5843) copied or moved without its .raw.png, then `ai-desktop grid --input copy.png`.

*Fix:* Choose candidates by `scale > 1` or the `zoom` field; when the image's own metadata has a `spacing` and no raw copy exists, refuse or warn that it is already gridded.

### `--spacing` without `--grid` is silently ignored

`grid-shot-9` · low · ux · **unverified** · `ai_desktop.py:3099`

cmd_screenshot draws a grid only when --grid or --zoom is given, so `screenshot --spacing 50` returns an un-gridded image with spacing=none and no hint. --radius and --factor without --zoom are dropped the same way.

*When:* An agent shortens the documented `--grid --spacing 50` to `screenshot --spacing 50`, gets an image without labels and estimates coordinates from bare pixels.

*Fix:* Let an explicit --spacing imply --grid, and raise a CliError when --radius or --factor is given without --zoom.

### Spacing is not checked against the shrink factor, so the grid can bury the image

`grid-shot-10` · low · robustness · **unverified** · `ai_desktop.py:385`

Line width grows with k = 1/shrink while lines move closer in saved pixels. An explicit fine spacing on a wide capture, or auto_spacing's nothing-fits fallback (line 336) in a zoomed-out zoom, leaves most pixels under grid ink.

*When:* `screenshot --grid --spacing 20` on a dual-monitor or 4K-at-100% desktop; `--zoom X,Y --radius 2000 --factor 1` on a 4K monitor (38 lines, 50 px apart).

*Fix:* Raise a spacing whose saved-image gap is under about four line widths and report the spacing used; let auto_spacing extend its candidates (x2, x5, x10) until one fits.

**Smaller notes (unverified):**

- regrid_source (lines 3227-3233) trusts metadata: a chunk with zoom but no image_scale/width, or image_scale 0, raises KeyError/ZeroDivisionError and prints a traceback instead of an ERROR line; `version` is never checked.
- `grid --input` on an image over about 178 MP raises PIL DecompressionBombError, which is not an OSError (checked), so main() re-raises it as a traceback (line 3237).
- known_pointer is read after the grid is drawn (line 2792), tens to hundreds of ms after the capture; with a moving pointer the marker and the pointer_x/y that --seen masks can disagree with the captured cursor.
- cursor=native is reported for a zoom even when the pointer lies outside the zoom box (line 2793).
- cmd_grid has no RAW_SUFFIX refusal: `grid --input shot.png -o shot.raw.png` overwrites the --seen reference (line 3262).
- The -o RAW_SUFFIX check (line 2762) is case-sensitive; on a case-insensitive filesystem `-o shot.Raw.png` overwrites shot.png's sidecar.
- Re-gridding a HiDPI zoom uses the logical-size raw copy (line 3235), so the result is blurrier than the original zoom made from physical pixels.
- A zoom saved as JPEG (`-o a.jpg --zoom ...`) has no own metadata, so `grid --input a.jpg` re-grids the whole capture instead of the zoom.
- JSON field types vary: spacing is int or "none", pointer_x/y int or "unknown", pruned int or "skipped" (lines 2808, 2837, 2840); null would be easier for clients.
- list_monitors runs twice per screenshot (inside capture_screen and at line 2767), so xrandr is spawned twice on Linux.
- An un-gridded, un-shrunk screenshot without a marker writes the same pixels twice (main file and .raw.png, line 2826); the raw copy could be skipped or linked.
- save_image writes straight to the final path (line 463); a parallel `--seen latest` can open a half-written PNG. Write to a temp name and os.replace.
- label_every thins by arbitrary multiples (line 341), giving label steps such as 60, 90 or 150; restricting the step to 1, 2, 5, 10 times the spacing reads better.
- Zooms smaller than about 60 screen px across (--radius 10 to 25 at low factor) get no lines or labels at all, because no ZOOM_SPACINGS candidate fits.
- Test gaps: no test for a fractional-scale HiDPI zoom, label collisions, the far_x/far_y thresholds, a non-PNG -o, a negative --zoom on the CLI, or re-gridding `grid` output.

**Improvement ideas:**

- Element overlay mode: draw numbered boxes from the accessibility tree (AT-SPI, UIA, AX) through this same pipeline, with metadata mapping each number to a screen rect, so agents click by element.
- Zoom and re-grid from the cached raw copy (`screenshot --zoom X,Y --from latest`): no new capture, no capture-tool delay, and the --seen reference stays the same.
- In a long-lived process (MCP or a daemon) keep the last capture in memory: skip the raw PNG write and re-decode, and return only changed tiles or a JPEG/WebP frame for live viewing.
- Put edge labels in a margin around the capture, recorded as padding in metadata, so top bars, tab strips and taskbars stay fully visible under a grid.
- Model profiles for --max-width and label size: vision models also cap total pixels, not just the long edge, so 1920x1080 is shrunk further than MODEL_VIEW_EDGE assumes; report estimated image tokens.
- Shrink first, then draw the grid at saved size for non-zoom captures too: crisper labels, one code path for zoom and full screen, and far less memory on large desktops.

## Screen capture, monitor detection and the screenshot store

Score 6.5: Clean, readable capture/monitor/store code with a careful prune design and 45 passing tests. But the xrandr primary marker is parsed wrongly (fixtures encode the mistake), tool timeouts escape as tracebacks, tool choice ignores the session, nothing is cached, and Windows/macOS detection has no unit tests.

### xrandr primary marker parsed wrongly: every auto monitor becomes primary

`capture-monitors-store-1` · high · bug · **verified** · `ai_desktop.py:585`

In `xrandr --listmonitors`, `+` means automatic (present on every normal monitor) and `*` means primary. The parser treats `+` as primary, so on multi-monitor Linux all monitors are flagged primary and index 0 / `--monitor primary` is simply the top-left monitor.

*When:* Two monitors on X11 or Xwayland where the real primary is not top-left. `monitors` prints `primary` on both; `screenshot --monitor primary` captures the wrong one, contradicting README line 148.

*Fix:* Use `"*" in flags`, correct the docstring at line 579, and replace the unrealistic TWO/NEG fixtures in tests/test_monitors.py:10-18 with real `+*` / `+` output.

### Screenshot-tool timeout escapes as a Python traceback

`capture-monitors-store-2` · medium · robustness · **verified** · `ai_desktop.py:525`

`subprocess.run(..., timeout=30)` raises `subprocess.TimeoutExpired`, which is neither CliError nor OSError. execute() re-raises it, so the CLI prints a traceback: no `ERROR ...` line and no JSON object with --json. The same applies to screencapture at line 797.

*When:* gnome-screenshot, grim, spectacle or screencapture hangs for 30 s (busy compositor, interactive portal fallback, permission prompt) during screenshot, a --seen guard or a wait poll.

*Fix:* Catch `subprocess.TimeoutExpired` (and UnicodeDecodeError) in grab_linux and _screencapture_rect and raise `CliError(f"{tool} timed out after 30 s")`; add a test.

### First installed screenshot tool always wins; no session match and no fall-through

`capture-monitors-store-3` · medium · robustness · **unverified** · `ai_desktop.py:494`

The comment says tools are 'tried in order', but only the first one installed is ever run. A tool that does not fit the session fails or captures the wrong thing, and the next tool or Pillow's X11 capture is never tried.

*When:* Sway or KDE Wayland with gnome-screenshot also installed (setup.sh installs it): it falls back to the Xwayland root, likely a black image. Or an X11 session with only grim: every capture fails.

*Fix:* Order candidates by XDG_CURRENT_DESKTOP and session type; on non-zero exit, empty file or timeout try the remaining tools (then Pillow XCB on X11). Make doctor check the tool suits the session.

### Monitor layout re-queried 5 to 8 times per action, uncached

`capture-monitors-store-4` · low · performance · **unverified** · `ai_desktop.py:692`

list_monitors() spawns `xrandr --listmonitors` on every call and nothing caches the result. One `click --monitor N --seen latest --shot` calls it 6 times; drag up to 8; each wait poll once more. Time cost not measured here.

*When:* Any guarded action with --shot, any `wait` loop, and every MCP call in the long-lived server.

*Fix:* Cache the detected monitors per command (reset in execute()), or with a short TTL in the MCP server; pass the list from capture_screen into take_screenshot and guard_seen.

### macOS Monitor.scale is always 1.0 on Retina displays

`capture-monitors-store-5` · low · bug · **unverified** · `ai_desktop.py:663`

`CGDisplayPixelsWide` returns the width in points on HiDPI modes (it is what pyautogui.size() uses, which this project treats as logical). Dividing it by the bounds width gives 1.0, so `monitors` reports scale=1 while `screenshot` reports scale=2.0.

*When:* `ai-desktop monitors` on any Retina Mac: text and JSON show `scale=1` for a 2x display.

*Fix:* Use `CGDisplayModeGetPixelWidth(CGDisplayCopyDisplayMode(display)) / width`, or NSScreen.backingScaleFactor; unit-test with a fake Quartz module.

### cursor=native is assumed, never verified

`capture-monitors-store-6` · low · bug · **unverified** · `ai_desktop.py:770`

Capture.cursor becomes "native" whenever a tool with a cursor flag exists (all three have one) or, on macOS, whenever it was requested (line 815). If the pointer is hidden, nothing is drawn, yet take_screenshot suppresses its own marker.

## Input: human-like pacing, the pyautogui and uinput backends, pointer commands

Score 6.5: The uinput backend, the only one used live, gets its kernel details right, and the pacing code is pure and well tested. The pyautogui side rests on unverified assumptions: the failsafe defeats the drag's button release, macOS drags and Windows scroll targeting look broken, and capital-letter hotkeys silently add Shift.

### pyautogui drag: a failsafe abort leaves the mouse button held

`input-1` · high · bug · **verified** · `ai_desktop.py:1406`

The finally block releases through pyautogui.mouseUp, which runs failSafeCheck() before doing anything. After a failsafe abort the pointer is still in the corner, so mouseUp raises again and the button stays pressed, contrary to the CHANGELOG ('released even if the move fails').

*When:* Windows, macOS or X11: the user slams the mouse into a corner while drag holds the button, or in the 0.1 s pauses around it. Exit 3, button still down; moving away keeps dragging.

*Fix:* Release with the failsafe bypassed: set gui.FAILSAFE = False around mouseUp and restore it afterwards. Add a test whose fake mouseUp raises FailSafeException while the pointer is 'in a corner'.

### macOS drag sends mouse-moved events, not drag events

`input-2` · high · bug · **verified** · `ai_desktop.py:1404`

The held move uses gui.moveTo, which on macOS posts kCGEventMouseMoved. While a button is down Cocoa expects kCGEventLeftMouseDragged (pyautogui's own source says so), so windows, sliders and selections most likely do not follow. This path has never run on a real Mac.

*When:* macOS: drag --x1 200 --y1 150 --x2 900 --y2 400 on a window title bar or over text. Press and release happen, but nothing is dragged or selected.

*Fix:* Use gui.dragTo(x2, y2, duration=duration, button=button, mouseDownUp=False) for the held move: drag events on macOS, plain moves elsewhere. Then confirm on a real Mac.

### Windows: scroll --x/--y does not put the pointer on the target

`input-3` · medium · bug · **unverified** · `ai_desktop.py:1428`

scroll relies on pyautogui.scroll(x, y) to land on the target. On Windows that call sends MOUSEEVENTF_WHEEL without MOVE, so x and y are ignored: with --instant the pointer never moves, with pacing it stops at the last waypoint, a few px short.

*When:* Windows: scroll --x 1500 --y 600 --instant (or MCP instant=true) while the pointer rests over another pane. That pane scrolls; the output still says OK with x=1500 y=600.

*Fix:* When x and y are given, call self.gui.moveTo(x, y) after the glide on every platform, then self.gui.scroll(clicks) without coordinates. Add a test that asserts the final moveTo.

### A capital letter in a hotkey silently adds Shift

`input-4` · medium · ux · **verified** · `ai_desktop.py:3328`

Key names are case-insensitive except single letters, where an uppercase letter means shift+letter on both backends. 'Ctrl+C' therefore sends Ctrl+Shift+C and 'Ctrl+W' sends Ctrl+Shift+W, with no warning, and neither README nor AGENTS mentions it.

*When:* An agent runs hotkey --keys Ctrl+W to close one tab: Chrome closes the whole window. Ctrl+C opens the DevTools inspector instead of copying.

*Fix:* In cmd_hotkey, lowercase single letters when ctrl, alt or meta is present (explicit 'shift' still works), or reject them with a hint. Document the rule and add a test.

### uinput sends X and Y as separate frames: L-shaped steps, staircase drags

`input-5` · medium · bug · **unverified** · `ai_desktop.py:1698`

emit() appends SYN_REPORT to every event, so each pointer move reaches the compositor as two motions: (new x, old y), then (new x, new y). A drag with the button held is a staircase, not the straight line the code comment promises.

*When:* Wayland: drag --x1 200 --y1 200 --x2 700 --y2 700 in a paint or diagram app that uses every motion event: 25 steps of 20 px right, then 20 px down.

*Fix:* Give emit a sync=False option (or a frame helper): write ABS_X and ABS_Y, then one SYN_REPORT. Keep the 1 px step-aside as its own frame; test the frame layout.

### A Wayland session started from a text console is detected as X11

`input-6` · medium · portability · **unverified** · `ai_desktop.py:206`

is_wayland() looks at WAYLAND_DISPLAY only when XDG_SESSION_TYPE is empty. A compositor started from a console login (sway without a display manager) inherits XDG_SESSION_TYPE=tty, so --backend auto picks pyautogui, whose XTest input cannot reach native Wayland windows.

*When:* Log in on a text console and start sway: XDG_SESSION_TYPE=tty, WAYLAND_DISPLAY=wayland-1. Clicks go through Xwayland and native windows ignore them; doctor reports an x11 session.

*Fix:* Treat the session as Wayland when the type is 'wayland', or when WAYLAND_DISPLAY is set and the type is not 'x11'. Add tests for 'tty' and unset.

### The drag failsafe path and the uinput device code are effectively untested

`input-7` · medium · test-gap · **unverified** · `tests/test_drag_monitor.py:43`

The riskiest input code has no real coverage. _UInputDevice (ioctl numbers, struct packing, emit, close) is always replaced by a fake, and the fake pyautogui never applies failsafe checks, so the drag-release test passes although the real release fails.

*When:* A wrong struct size or ioctl order, or the failsafe-in-finally bug above, passes all 278 tests.

*Fix:* Test _UInputDevice with patched os.open, os.write and fcntl.ioctl: assert each ioctl's size bits equal struct.calcsize and check event order. Give fake_gui a failsafe-aware mode.

### A bad AI_DESKTOP_UINPUT_DELAY crashes after the device is created

`input-8` · low · robustness · **unverified** · `ai_desktop.py:1693`

The delay is parsed with float() after UI_DEV_CREATE and outside the try block. A typo, a negative value or 'nan' raises ValueError: a traceback instead of the ERROR or JSON line, and the device is never closed (one leaked virtual device per MCP call).

*When:* Wayland: AI_DESKTOP_UINPUT_DELAY=0,5 ai-desktop --json click --x 500 --y 300 prints a Python traceback, no JSON object, and does not click.

*Fix:* Parse the value before opening the device; fall back to 0.5 when it is invalid, negative or not finite (as shot_settle() does) and cap it.

### X11 multi-monitor: the failsafe corners are not the primary screen's corners

`input-9` · low · docs · **verified** · `README.md:12`

On X11 pyautogui's size() is the whole X root, so the abort corners are those of the bounding box of all monitors. README and AGENTS promise 'any corner of the primary screen'; some of those do not abort, and some real ones are unreachable.

*When:* X11, primary 1920x1080 at 0,0 plus 2560x1440 at 1920,0: the primary's bottom-left (0,1079) does not abort, and the failsafe point (0,1439) is on no monitor.

*Fix:* On X11 set pyautogui.FAILSAFE_POINTS to the outer corners of every monitor and use the same list in check_point and confine_point, or correct README and AGENTS.

**Smaller notes (unverified):**

**Improvement ideas:**

- Wayland stop switch: there is no failsafe on Wayland, so poll a stop file or a physical key (evdev) between waypoints, characters and drag steps.

- With accessibility data (AT-SPI, UIA, AX), check which element is under the target before pressing, and use shorter, straighter glides; today's curve swerves up to 17% of the distance sideways.

## Stale-screen guard (--seen), --shot, wait and run

Score 6: Thoughtfully built and well tested (51 passing tests here), with good failure handling around --shot and run. But the whole-screen guard misses the typical dialogs it claims to catch, the guard-to-click gap reaches about 2 s, wait --stable is satisfied too early, and run has validation, encoding and log-privacy edge defects.

### Whole-screen --seen check lets ordinary modal dialogs through

`guard-wait-run-1` · high · bug · **verified** · `ai_desktop.py:3027`

key, hotkey, type and paste abort only when more than 10% of the whole capture's fingerprint cells changed. Ordinary confirmation dialogs cover 2-8%, so they pass, contradicting the README ('a dialog doesn't') and the MCP instructions.

*When:* A 'Save changes?' or 'Delete?' dialog opens after the screenshot; `key --key enter --seen latest` passes with seen_diff about 0.05 and presses Enter in the dialog. Worse on large or multiple monitors.

*Fix:* Judge absolute size, not share: abort when changed cells form a connected block of roughly 200x100 px or more, per monitor; also record and compare the active window where the platform exposes it.

### Guard runs up to about 2 s before the click it protects

`guard-wait-run-2` · medium · robustness · **unverified** · `ai_desktop.py:3273`

The guard captures first; afterwards the uinput device is created (0.5 s sleep) and the pointer glides (0.15-1.5 s). Nothing is re-checked, so a popup or layout shift in that window gets the click. README says 'just before acting'.

*When:* Default paced click on Wayland while a page still loads: a cookie banner shifts the button one second after the guard capture, and the click lands on whatever is there now.

*Fix:* Lease the device and glide to within a short hop of the target before capturing; compare, then do the last hop and press. Alternatively re-check the patch after the glide.

### wait --stable reports stable before loading starts or while a spinner turns

`guard-wait-run-3` · medium · design · **unverified** · `ai_desktop.py:3510`

Stable means one pair of captures about 0.5 s apart differing in at most 0.5% of cells (11 of 2304). A window that has not appeared yet, a stalled page or a spinner all qualify, so the documented launch-then-wait recipe can return the old screen.

*When:* `launch-chrome`, then `wait --stable --shot` where captures are fast (X11, Windows, macOS) or the launch is slow: polls=2 after about 0.6 s, and the shot shows the pre-launch screen.

*Fix:* Add a changed-then-stable mode (reference: latest screenshot) and require quiet for a minimum time across several captures with a finer diff; use it in the README and AGENTS recipes.

### run checks only argument syntax up front; later steps fail after earlier ones acted

`guard-wait-run-4` · medium · robustness · **unverified** · `ai_desktop.py:3602`

Up-front validation is only argparse. Errors the commands raise themselves (non-ASCII type text, unknown key, bad hotkey, failsafe corner, off-screen point, missing --seen file) surface mid-sequence after earlier steps acted, despite 'every step is checked first'.

*When:* `run` with [click, type 'Hello — world', key enter]: the click happens, type fails on the em dash (done=1, failed=2); an agent that retries the run clicks twice.

*Fix:* Give each command a side-effect-free validate(args) (TYPEABLE, resolve_key, hotkey split, check_point, --seen file exists) and have run call all of them before the first step acts.

### run prints copied text with print(): crash on a non-UTF-8 stdout after the steps ran

`guard-wait-run-5` · medium · portability · **unverified** · `ai_desktop.py:3650`

copy and clipboard get write UTF-8 bytes via print_text, but run uses print(). With a cp1252 stdout (Windows, output piped) copied text such as '✓' or CJK raises UnicodeEncodeError after 'OK run' was printed: traceback and exit 1 although every step succeeded.

*When:* Windows agent captures the output of `run --steps '[["hotkey","--keys","ctrl+a"],["copy"]]'`; the selection holds a character outside cp1252. The agent sees a failure and may repeat the run.

*Fix:* Move print_text's UTF-8 writer into a helper and use it in cmd_run with the same trailing-newline rule; add a test that swaps in a cp1252 stdout.

### Unbalanced-quote error echoes the whole step, typed text included, into the action log

`guard-wait-run-6` · medium · privacy · **verified** · `ai_desktop.py:3551`

split_step's error embeds the whole command string. A string step whose text contains an apostrophe puts that text on stderr and into the action log's result.error, although typed text is promised never to be stored and nearby code avoids echoing arguments.

*When:* `run --steps '["type --text it's my password hunter2"]'`: exit 2, and the sentence is in ~/.ai-desktop/logs/actions-*.jsonl.

*Fix:* Report only the step number and first token ('step 1 (type): unbalanced quote; use a list of arguments'); assert the log stays clean in test_run_reports_an_unbalanced_quote.

### A bad run step produces a multi-line ERROR containing the full argparse usage

`guard-wait-run-7` · low · bug · **verified** · `ai_desktop.py:3604`

A step that fails parsing is reported with parse_quiet's captured text: the argparse usage block plus the error. The ERROR output spans 4-6 lines (270-470 characters), breaking the one-line contract; only 'unrecognized arguments' is condensed.

*When:* `run --steps '[["key","--key","enter"],["bogus"]]'` in text mode prints the usage of ai-desktop inside the ERROR message.

*Fix:* Keep only the text after the last 'error: ' of the argparse output, or use an ArgumentParser subclass whose error() raises with the bare message.

### shot_error can contain newlines and quotes, splitting the OK line

`guard-wait-run-8` · low · robustness · **unverified** · `ai_desktop.py:3078`

shot_fields copies the exception text into shot_error, and capture errors carry the tool's raw stderr. format_fields quotes values but escapes nothing, so multi-line stderr gives a multi-line OK line and embedded quotes make it ambiguous.

### run --file: undecodable or BOM-prefixed files give a traceback or a confusing error

`guard-wait-run-9` · low · portability · **unverified** · `ai_desktop.py:3566`

Reading --file catches only OSError. A UTF-16 file (PowerShell 5 redirection) raises UnicodeDecodeError, a ValueError, so run ends in a traceback; a UTF-8 BOM yields the confusing 'Unexpected UTF-8 BOM' JSON error.

### Pointer mask hides the click target after a previous click there

`guard-wait-run-10` · low · robustness · **unverified** · `ai_desktop.py:2887`

With a tool-drawn pointer, 57x57 px around the recorded and current pointer positions are excluded from the patch. After `click --shot`, a guarded click at or near the same spot ignores any change that fits under the mask.

`windows-chrome-8` · low · security · **unverified** · `ai_desktop.py:3438`

### Win32 focus: ALT tap fallback is fragile and can leave a menu active

`windows-chrome-10` · low · robustness · **unverified** · `ai_desktop.py:2185`

## Clipboard, copy/paste, position and doctor

Score 5.5: The GNOME Wayland path is careful (stdin transport, background-owner handling, sentinel) and doctor is useful. But the clipboard layer has no tests, error paths leave the clipboard clobbered or break the output contract, tool choice is likely wrong on KDE/wlroots, the Windows path has a path-search and an encoding hole, and doctor misses real failure states.

### X clipboard tools are preferred on every Wayland compositor, but only GNOME shares them unconditionally

`clipboard-doctor-1` · high · bug · **unverified** · `ai_desktop.py:2325`

With DISPLAY set, xclip/xsel beat wl-clipboard on every Wayland session. KWin and wlroots bridge the Xwayland clipboard only while an X11 window is focused, so paste --text pastes the old clipboard yet reports OK, and clipboard get/copy return empty text.

*When:* KDE Plasma or Sway/Hyprland Wayland session, xclip installed, a native Wayland window focused: `paste --text "new"` inserts whatever was on the clipboard before.

*Fix:* Prefer wl-copy/wl-paste when WAYLAND_DISPLAY is set and XDG_CURRENT_DESKTOP is not GNOME; read the clipboard back after setting and fail before pressing paste if it differs.

### copy leaves its sentinel on the clipboard when the key press or the polling fails

`clipboard-doctor-2` · medium · bug · **unverified** · `ai_desktop.py:3366`

cmd_copy overwrites the clipboard with a sentinel and restores the previous text only on the nothing-copied path. Any exception from hotkey or get_clipboard (no /dev/uinput access, corner failsafe, Ctrl+C, tool error) leaves ai-desktop-copy-<hex> there and loses the user's clipboard.

*When:* Wayland without the udev rule: every `copy` replaces the clipboard, then fails in hotkey. Or `copy` run in the focused terminal: the injected ctrl+c interrupts ai-desktop itself.

*Fix:* Wrap everything after set_clipboard(sentinel) in try/finally that restores `previous` while the clipboard still holds the sentinel; open the input device before touching the clipboard.

### Clipboard tool timeout escapes as a traceback instead of an ERROR line

`clipboard-doctor-3` · medium · robustness · **verified** · `ai_desktop.py:2362`

The 15 s clipboard timeout raises subprocess.TimeoutExpired, which is neither CliError nor OSError, so execute() re-raises it: a traceback instead of `ERROR ...` or a JSON object. The xrandr and osascript calls catch SubprocessError; the clipboard calls (also line 2350) do not.

*When:* `xclip -o` waiting on a frozen selection owner, wl-paste waiting for focus on GNOME, or a very slow PowerShell start: `clipboard get`, `copy`, `paste --text` crash after 15 s.

*Fix:* Catch subprocess.TimeoutExpired in set_clipboard and get_clipboard and raise CliError naming the tool; use a shorter timeout (about 5 s) for reads.

### PowerShell is launched by bare name, so a powershell.exe in the working directory wins

`clipboard-doctor-4` · medium · security · **unverified** · `ai_desktop.py:2308`

PowerShell is started by bare name. Windows CreateProcess searches the current directory before System32, so a powershell.exe in the agent's working directory (for example a cloned repository) runs instead of the real one on every copy, paste --text and clipboard call.

*When:* Windows, agent or MCP server started in an untrusted project folder that contains powershell.exe; the agent calls `ai-desktop clipboard get`.

*Fix:* Use the absolute path %SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe and make doctor check that this file exists.

### run prints copied text with print(), which crashes on Windows pipes after the OK line

`clipboard-doctor-5` · medium · bug · **unverified** · `ai_desktop.py:3650`

In text mode `run` prints copied text with print(), which uses the pipe's encoding; print_text writes UTF-8 bytes. On Windows pipes (cp1252) a character such as a check mark raises UnicodeEncodeError after `OK run` was printed: traceback and exit 1 although every step ran.

*When:* Windows, Python before 3.15, stdout piped to an agent, `run --steps '[["copy"]]'` or `[["clipboard","get"]]` with an emoji, CJK text or a check mark on the clipboard.

*Fix:* Send the step texts through the same UTF-8 buffer writer as print_text (one shared helper), keeping its trailing-newline rule.

### doctor calls a Wayland desktop x11 and passes when XDG_SESSION_TYPE is not exactly wayland

`clipboard-doctor-6` · medium · bug · **unverified** · `ai_desktop.py:2489`

is_wayland() (line 206) is false whenever XDG_SESSION_TYPE is set to anything but wayland (Sway or Hyprland started from a TTY has `tty`). Doctor then labels the session x11, validates the pyautogui backend, which reaches only Xwayland windows, and reports everything ok.

*When:* XDG_SESSION_TYPE=tty with WAYLAND_DISPLAY=wayland-1: doctor prints `ok session x11 (... WAYLAND_DISPLAY='wayland-1')`; clicks on native windows then do nothing.

*Fix:* Treat a set WAYLAND_DISPLAY as Wayland unless XDG_SESSION_TYPE is x11; in doctor, warn whenever the two variables disagree.

### copy destroys non-text clipboard contents and pollutes clipboard history

`clipboard-doctor-7` · medium · bug · **unverified** · `ai_desktop.py:3364`

copy saves only the clipboard's plain text before overwriting it. With nothing selected, an image, copied files or rich text is replaced by an empty string or plain text. Every copy also adds ai-desktop-copy-<hex> to clipboard history managers and cloud clipboard sync.

*When:* The user has a screenshot or cut files on the clipboard; the agent runs `copy` with nothing selected: the content is gone and the pending file move is lost.

*Fix:* Detect the change without overwriting: GetClipboardSequenceNumber on Windows, NSPasteboard changeCount on macOS, the X11 TIMESTAMP target on Linux; keep the sentinel only as a fallback, marked transient.

### wl-clipboard commands carry no type: images come back as garbage text

`clipboard-doctor-8` · medium · bug · **unverified** · `ai_desktop.py:2331`

The wl-clipboard commands name no type. Without text on the clipboard wl-paste outputs the first offered format, so an image returns megabytes of mangled bytes instead of an empty string; wl-copy guesses a MIME type from content, which can make text unpasteable.

*When:* Wayland session where wl-clipboard is the chosen tool (no xclip or xsel), a screenshot on the clipboard, then `clipboard get` or `copy` (reading `previous`).

*Fix:* Use `wl-copy --type text/plain` and `wl-paste --no-newline --type text`; the existing "not available" check then maps a non-text clipboard to an empty string.

### The whole clipboard layer and the copy sentinel logic have no tests

`clipboard-doctor-9` · medium · test-gap · **unverified** · `ai_desktop.py:3360`

No test exercises cmd_copy, cmd_paste, `clipboard set`, _clipboard_tools, set_clipboard or get_clipboard; the only clipboard tests stub them out. The sentinel loop also uses time.sleep and time.monotonic instead of the _sleep/_now hooks, so the fake clock cannot drive it.

*When:* A regression in tool choice, the empty-clipboard mapping, sentinel restore or the paste ordering passes CI on all three platforms.

*Fix:* Add tests with a fake subprocess.run and backend: tool selection per environment, error mapping, copy success, nothing-selected and exception restore, paste order; switch cmd_copy to _sleep/_now.

### copy and paste shortcuts depend on the keyboard layout on Wayland, contrary to the README

`clipboard-doctor-10` · low · docs · **unverified** · `ai_desktop.py:2389`

On the uinput backend copy and paste press the physical C and V keys of a US board. README line 423 says `paste --text` doesn't depend on the layout, but on layouts that move those letters (Dvorak, Workman, Bepo) another shortcut is sent, e.g. ctrl+k.

*When:* GNOME Wayland with a Dvorak layout: `paste --text "x"` presses ctrl+k (delete to end of line or search, depending on the app); `copy` presses ctrl+j.

*Fix:* Send ctrl+Insert and shift+Insert (or KEY_COPY/KEY_PASTE where honoured) on uinput; otherwise correct the README sentence and have doctor warn about non-QWERTY layouts.

## MCP server

Score 6: Small, readable adapter that reuses the CLI path, is serialised by a lock and has a real stdio test. But cancellation and timeouts cannot stop or dequeue actions, paste mangles JSON-like text (null pastes the old clipboard), crashes and failures lose their detail, and inline PNGs are unbounded. Those matter on a real desktop.

### Cancelled or timed-out calls keep acting; queued ones still run later

`mcp-1` · high · robustness · **verified** · `ai_desktop_mcp.py:60`

Tools are synchronous, so the SDK runs them with anyio.to_thread.run_sync (not abandonable) and they block on a threading.Lock. A client cancel or timeout stops nothing: the running action finishes, and calls queued behind the lock still execute afterwards.

*When:* User presses stop during a 350-character type (about 61 s), or a 60 s client timeout fires: typing continues, a queued click still lands, a retry types twice. Wayland has no failsafe.

*Fix:* Make tools async; queue on an anyio lock so waiting calls can be cancelled; run execute in a thread with a cancel flag checked in _sleep, typing, glide and poll loops; send progress notifications.

### paste(text="null") pastes the old clipboard; JSON-looking text is rejected

`mcp-2` · high · bug · **verified** · `ai_desktop_mcp.py:272`

paste declares text as `str | None`, so the SDK's pre_parse_json JSON-decodes the value. Text `null` becomes None and the tool pastes whatever was already on the clipboard; text that is a JSON array or object fails validation and cannot be pasted.

*When:* paste(text="null") pastes the user's previous clipboard, possibly private, into the focused field. paste(text='{"a": 1}') or '[1, 2]' returns 'Input should be a valid string'.

*Fix:* Annotate text as plain `str` (default "" meaning clipboard only, or a separate tool); the SDK skips plain str. Do the same for title, url, zoom and seen; add a regression test.

### Unexpected exceptions escape run_raw and reach the model as a bare 'Error executing tool X'

`mcp-3` · medium · robustness · **unverified** · `ai_desktop_mcp.py:62`

run_raw's docstring promises not to raise, but execute re-raises anything that is not CliError, OSError or the failsafe. The SDK then hides the text, so the model sees no reason and the payload execute prepared is discarded.

*When:* gnome-screenshot, screencapture, xclip or wl-paste hangs past its timeout (ai_desktop.py:525, 799, 2350, 2362): subprocess.TimeoutExpired is not an OSError, so the result is only 'Error executing tool screenshot'.

*Fix:* Catch Exception around execute in run_raw and return (1, ai_desktop.LAST_PAYLOAD or a 'Type: message' payload), as cmd_run already does at ai_desktop.py:3625; add a test with a raising execute.

### Failed commands lose every payload field, including run's completed-step results

`mcp-4` · medium · design · **unverified** · `ai_desktop_mcp.py:72`

run() converts a failure into CommandError carrying only the error string. The exit code, the `results`, `done` and `failed` fields of a partly executed run, and wait's diff and polls are dropped; only doctor bypasses this. No screenshot accompanies the error.

*When:* run(steps=[copy, click --seen latest, type]) where the click's guard fails: the text copied in step 1 and the per-step results never reach the model, which must re-inspect everything.

*Fix:* Return CallToolResult(is_error=True) with the JSON payload as text (the SDK passes it through) and, for --seen mismatches and failed run or wait calls, attach a fresh screenshot.

### Inline screenshots are PNG only with no byte budget

`mcp-5` · medium · robustness · **unverified** · `ai_desktop_mcp.py:95`

Every screenshot and shot=true result is the whole PNG file, base64-encoded, with no size check. Photographic or video content at 1920 px exceeds 1 MB, and max_width=0 removes the only bound, so clients with result-size caps reject the call.

*When:* A screenshot of a browser showing photos or video in a client that caps tool results near 1 MB (reported for Claude Desktop), or max_width=0 on a 4K or multi-monitor desktop.

*Fix:* Encode the inline copy as JPEG or WebP (keep the PNG on disk), enforce a byte budget by lowering quality or width, and report the applied scale in the JSON.

### Tool schemas reject an integer monitor and numeric or string run steps

`mcp-6` · low · ux · **unverified** · `ai_desktop_mcp.py:258`

monitor is typed str although the monitors tool reports integer indexes, and run's steps is list[list[str]] although the CLI accepts numbers and command strings. Pydantic does not coerce int to str, so these natural calls fail validation and cost a round trip.

*When:* screenshot(monitor=1), click(x=5, y=6, monitor=1), run(steps=[["click","--x",500,"--y",300]]) or run(steps=["key --key enter"]).

*Fix:* Type monitor as `int | str` and steps as `list[list[str | int | float] | str]` (the CLI already handles both); add tests for each form.

### wait(stable=false) is silently ignored

`mcp-7` · low · bug · **unverified** · `ai_desktop_mcp.py:253`

The wait tool advertises a `stable` boolean that the code never reads: without `changed` it always passes --stable, with `changed` it always waits for a change. The parameter only misleads the model.

*When:* wait(stable=false, timeout=5) expecting a plain pause: it polls for stability and can fail with 'screen still changing' on a page with animation.

*Fix:* Remove `stable`, or use `mode: Literal["stable", "changed"]` with a `reference`; expose the CLI's `monitor` and `interval` while there.

### open_world_hint=False on tools that drive a signed-in browser

`mcp-8` · low · design · **unverified** · `ai_desktop_mcp.py:32`

Every action tool, including launch_chrome(url), is annotated open_world_hint=False, which tells clients the tool cannot reach external systems. These tools click and type in signed-in web apps, so a client that relaxes confirmation for closed-world tools under-protects the user.

*When:* A client that uses openWorldHint when deciding whether to confirm: launch_chrome(url=...) or a click on Send in webmail is presented as a local-only action.

*Fix:* Set open_world_hint=True on ACTION (at least launch_chrome, click, type, key, hotkey, paste, run) and keep False only for monitors, position, log and screenshots_latest.

### The long-lived server repeats one-shot CLI work on every call

`mcp-9` · low · performance · **unverified** · `ai_desktop_mcp.py:58`

Each call takes the one-shot CLI path: the argparse parser is rebuilt (about 5 ms, twice per run step), xrandr is spawned on every list_monitors, and screenshots are encoded to disk, then re-read and base64-encoded. Nothing is reused between calls.

*When:* click(seen="latest", shot=true) on Linux: five xrandr spawns, two external captures, a reference PNG decode, two PNG encodes and a 0.4 s settle for one click.

*Fix:* Add a server session: cached parser, monitor layout with a short TTL, reused backend, and the last capture and fingerprint kept in memory for seen, wait and shot.

### MCP tests skip concurrency, cancellation, error mapping and half the tools

`mcp-10` · low · test-gap · **unverified** · `tests/test_mcp.py:121`

The eight tests check argv construction and one stdio round trip. Nothing covers overlapping calls, a cancelled call, a raising execute, shot="error", JSON-like paste text, or the drag, focus, launch_chrome, copy, clipboard, position, windows, monitors and doctor tools.

*When:* A regression in the lock, in _with_shot's error branch or in an untested tool's argv (for example drag's --duration) passes CI unnoticed.

## Cross-cutting findings

Checked across areas; several overlap with findings above.

### split_step error message carries the whole step text into the action log

`seed-1` · medium · privacy · **verified** · `ai_desktop.py:3550`

When a command-string step of run has an unbalanced quote, split_step raises CliError whose message contains the whole step (repr), including any --text. cmd_run takes care not to echo unrecognised arguments for exactly this reason, but this message is logged as result.error by log_action.

*When:* run --steps with a step such as: type --text it's my secret (unbalanced quote)

*Fix:* Do not include the step text in the message (name the command only), or redact error text for steps.

*Correction from the check:* An unbalanced quote in a run command-string step writes that whole step, including any --text, to the local action log, breaking the README privacy promise. Nothing is typed; exposure is limited to the user's own log file.

### uinput absolute moves are sent as two frames (X, then Y)

`seed-2` · medium · robustness · **unverified** · `ai_desktop.py:1696`

_UInputDevice.emit() writes each event followed by its own SYN_REPORT, so _emit_abs delivers a move as two frames: first the new X with the old Y, then the new Y. The pointer visits an intermediate point on every step, drags follow a staircase, and the event count doubles.

*When:* Any move, click or drag on the Wayland uinput backend

*Fix:* Add a way to emit several events before one SYN_REPORT and use it for ABS_X+ABS_Y (and for shift+key).

### A screenshot and its .raw.png sidecar are pruned independently

`seed-3` · medium · bug · **unverified** · `ai_desktop.py:919`

prune_store treats every store file on its own. The size rule pops the oldest file first, so it can delete a screenshot and keep its sidecar or the reverse; the age rule can split a pair at the cutoff. CHANGELOG says the sidecar is pruned with its screenshot.

*When:* Store at the size limit, or a pair whose mtimes straddle the age cutoff; --seen on the survivor then fails or an orphan sidecar lingers

*Fix:* Group each screenshot with its sidecar and delete or keep them together.

### Monitor layout is re-detected (xrandr subprocess) several times per command

`seed-4` · medium · performance · **unverified** · `ai_desktop.py:692`

list_monitors() spawns xrandr on every call and is called repeatedly within one command: to_global, Backend.check_point, capture_screen, guard_seen (twice), take_screenshot and known_pointer each call it. A guarded click with --shot runs xrandr many times.

*When:* click --x 500 --y 300 --seen latest --shot on Linux

*Fix:* Cache the monitor list per command (and for the life of a daemon, invalidated on change).

### No human abort mechanism on the Wayland uinput backend

`seed-5` · high · security · **verified** · `ai_desktop.py:4086`

EXIT_FAILSAFE (3) only comes from pyautogui.FailSafeException. The uinput backend cannot read the pointer position and has no other abort, so on GNOME Wayland moving the mouse into a corner does nothing. Check whether README, AGENTS.md and the MCP instructions present the failsafe as available without saying it is missing on Wayland.

*When:* A user on Wayland tries to stop a runaway agent by slamming the mouse into a corner; the actions continue

*Fix:* Document it; add an abort that works everywhere (a stop file or stop command checked before every action, and physical-input detection or a hotkey in the daemon).

### The whole-screen --seen check for keyboard actions lets small modal dialogs through

`seed-6` · high · robustness · **verified** · `ai_desktop.py:2861`

For type, key, hotkey and paste the guard compares a 64x36 grey fingerprint and aborts only above 10 percent changed cells. A confirmation dialog of about 400x200 px on a 1920x1080 screen changes roughly 4 percent of the cells, so the guard passes and the keystroke (for example enter) goes to the dialog. The docs say a dialog does not pass.

*When:* Screenshot, then a small dialog appears, then key --key enter --seen latest

*Fix:* For keyboard actions also compare what has keyboard focus (active window, later the focused accessibility element) and/or flag any compact cluster of changed cells instead of only the global share.

### Time gap between the --seen check and the click

`seed-7` · medium · design · **unverified** · `ai_desktop.py:3272`

guard_seen runs before the action, but on Wayland the action then creates a uinput device (0.5 s sleep) and glides for up to 1.5 s before pressing. The screen can change in that window of up to about 2 s, which is longer than the gap the guard is meant to close.

*When:* A dialog or page reflow lands during the glide; the click goes to the new content

*Fix:* Re-check the target patch after the glide, immediately before the button press (cheap once captures are fast), or glide first and guard last.
